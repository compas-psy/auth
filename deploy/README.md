# Публикация SimpasID на `auth.cmpas.ru`

Сервис живёт на том же боевом сервере, что и `cmpas.ru` (`45.144.30.190`), но в отдельном
контуре. Общим остаётся **только железо и nginx**.

## Что произойдёт при применении

| Что появится | Где | Задевает ли соседа |
|---|---|---|
| Проект Compose `simpasid` | `/var/www/auth.cmpas.ru` | нет: свой каталог, рядом с `cmpas.ru` и `zapiski`, но отдельный |
| Свой Postgres 16 | контейнер `simpasid-postgres` | нет: своя база, свой том `simpasid_db`, порт наружу не публикуется вовсе |
| Приложение | контейнер `simpasid-app` | нет: слушает `127.0.0.1:3100`, наружу выходит через nginx |
| Том с ключами подписи | `simpasid_keys` | нет |
| vhost nginx | `/etc/nginx/sites-available/auth.cmpas.ru` | нет: маршрутизация по `server_name`, конфигурация `cmpas.ru` не читается и не правится |
| Сертификат | `/etc/letsencrypt/live/auth.cmpas.ru/` | нет: `certbot -d auth.cmpas.ru`, сертификат соседа не затрагивается |

**Чего в контуре нет:** ни одной ссылки на базу, том или сеть ПРАКТИКИ. Проверяется тестом
`server/test/isolation.test.ts` — не обещанием.

## Что делает человек

Ровно два действия, оба разовые.

**1. A-запись** у регистратора `cmpas.ru`:

```
auth.cmpas.ru.  A  45.144.30.190
```

На 06.09.2026 записи нет — проверено. Без неё certbot не выпустит сертификат.

**2. Три секрета** в `Settings → Secrets and variables → Actions` репозитория `auth`:

| Секрет | Что это |
|---|---|
| `SERVER_HOST` | `45.144.30.190` |
| `SERVER_USER` | тот же пользователь, что у выкладки `cmpas.ru` |
| `SSH_PRIVATE_KEY` | тот же ключ, что у выкладки `cmpas.ru` |

Это те же три значения, которые уже заведены в репозитории `cmpas.ru`, — новых сущностей
заводить не нужно.

`SIMPASID_DB_PASSWORD` задавать **не обязательно**: если секрета нет, выкладка заведёт пароль
сама при первом запуске и запомнит его в `.env` на сервере. Задать его стоит только если
пароль базы должен быть известен заранее.

Больше от человека ничего не требуется. Ключи подписи, миграции, конфигурация прокси и
сертификат делаются из репозитория.

## Порядок

1. Появляется A-запись (действие человека № 1).
2. Заводятся три секрета (действие человека № 2).
3. `Actions → Развернуть auth.cmpas.ru (nginx + TLS) → Run workflow`. Ставит vhost и выпускает
   сертификат. Повторный запуск безвреден.
4. Слияние в `main` запускает выкладку.

Шаги 3 и 4 можно поменять местами: до появления vhost сервис просто не виден снаружи.

## Как проверить, что получилось

```bash
curl -sS https://auth.cmpas.ru/.well-known/openid-configuration | head -5
# ждём 200 и "issuer":"https://auth.cmpas.ru"

curl -sI https://auth.cmpas.ru/healthz | head -3
curl -sI http://auth.cmpas.ru/ | head -3          # ждём 301 на https
curl -sI https://auth.cmpas.ru/ | grep -i strict  # ждём HSTS

curl -s -o /dev/null -w '%{http_code}\n' https://cmpas.ru/   # сосед жив

ssh <сервер> 'docker stats --no-stream simpasid-app simpasid-postgres'
```

Последняя проверка обязательна: лимит памяти задан 512 МБ на службу, и превышение надо увидеть
до того, как его увидит ядро.

## Как откатить

Полностью, одной строкой, без последствий для соседа:

```bash
ssh <сервер> 'cd /var/www/auth.cmpas.ru && docker compose -p simpasid down'
ssh <сервер> 'rm -f /etc/nginx/sites-enabled/auth.cmpas.ru && nginx -t && systemctl reload nginx'
```

Данные при этом остаются в томах `simpasid_db` и `simpasid_keys`. Удалять их (`down -v`) стоит
только осознанно: вместе с `simpasid_keys` уйдут ключи подписи, и все выданные токены
перестанут проверяться.

Откат одной выкладки — обычный `git revert` и повторная выкладка.

## Чего этот контур не делает

* Не трогает базу, тома и сеть ПРАКТИКИ.
* Не публикует наружу ни один порт, кроме того, что слушает nginx.
* Не хранит ключи подписи в git и в образе: сервис заводит их себе сам в томе, режим 600,
  в лог печатается только `kid`.
* Не выполняет production-деплой без явного разрешения владельца: выкладка запускается
  слиянием в `main` или кнопкой, а не сама по себе.
