# Внешние способы входа: что нужно получить от человека

Составлено по `CLAUDE.md` («Агент готовит перечень требований и вопросы — не более»),
`12_NATIVE_AUTH.md` §6 и `design/ЧИТАТЬ_ПЕРВЫМ.md`.

## Почему этого нет в Э2

`docs/plan/E2.md`, «Границы плана»: **T‑ID, Сбер ID и VK ID — это Э5**, отдельный план.
Яндекс ID в границах Э2 тоже не назван. Поэтому в сервисе сейчас **ноль подключённых
провайдеров**, и это состояние проверяется тестами, а не подразумевается:

* `GET /v1/auth/methods` возвращает `providers: []`;
* маршрут обмена отвечает `400 provider_unavailable` для любого провайдера;
* экран входа показывает только почту — блок провайдеров это выдерживает
  (`portal/test/signin.spec.tsx`, «блок не разваливается при нуле»);
* строка «Провайдер увидит, что вы вошли в СИМПАС, и когда» остаётся на экране всегда.

И-5 при этом соблюдён: почта есть всегда и остаётся способом входа по умолчанию.

**Механизм подключения готов и закрыт тестами.** Не хватает ровно внешних сведений: адаптер
регистрируется одной строкой `registerNativeAdapter`, веб-провайдер — записью в реестре.
Работа на одного провайдера — оценка: половина дня, способ получения оценки — объём
`services/providers/native.ts` и уже написанный контракт `NativeAdapter`.

## Что нужно по каждому провайдеру

Одинаково для всех четырёх. Секреты **не присылать в переписке** — они кладутся в секреты
репозитория, как уже сделано с ключами деплоя.

### Для входа в вебе (OIDC с редиректом)

| Что | Зачем |
|---|---|
| `client_id` и `client_secret` приложения | обмен кода на личность |
| Зарегистрированный `redirect_uri` **`https://auth.cmpas.ru/callback/<провайдер>`** | точное совпадение, без шаблонов — иначе провайдер откажет |
| Адреса authorize / token / userinfo **или** адрес discovery | построение запроса |
| Какие поля отдаёт провайдер и **есть ли среди них признак подтверждения почты** | без подтверждённой почты вход ведёт на экран C2 (И-5) |
| Требования брендбука к кнопке: вид, размер, подпись | сетка блока рассчитана под замену нейтральной кнопки фирменной без перекомпоновки |

### Дополнительно для мобильного входа

| Что | Зачем |
|---|---|
| Есть ли Android-SDK и какой | без него провайдер на мобильном экране не показывается — это следствие требования §2.2 |
| Разрешают ли правила провайдера схему «SDK отдаёт код приложению → код уходит на наш сервер → сервер меняет его на личность» | схема стандартная, но у конкретного провайдера могут быть условия |
| Ограничения по типам приложений | могут запрещать наш случай |

## Яндекс ID — отдельно, потому что он у вас уже есть

В выкладке `cmpas.ru` есть `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET`
(`.github/workflows/deploy-docker.yml`, проверено чтением). Но это регистрация **ПРАКТИКИ**,
с её собственным `redirect_uri`.

Два пути, оба требуют действия человека в кабинете Яндекса:

1. **Добавить второй `redirect_uri`** `https://auth.cmpas.ru/callback/yandex` в то же
   приложение и передать те же `client_id` и `client_secret` в секреты репозитория `auth`.
   Быстрее.
2. **Завести отдельное приложение** для сервиса идентичности. Чище: отзыв или ротация ключа
   у одного не задевает другой, и в журнале Яндекса видно, кто именно ходил.

Рекомендую второй: сервис идентичности и продукт — разные субъекты, и общий ключ связывает
их судьбы без нужды.

**Замечание, которое важнее выбора пути.** После переезда ПРАКТИКИ на единый вход её
собственная кнопка «Войти через Яндекс» станет лишней: вход через Яндекс будет идти через
СИМПАС. Но выключать её нельзя до конца наблюдения (принцип аддитивности, чек-лист переезда
п. 7) — какое-то время оба пути живут рядом, и человек может войти любым.

## Вопросы, на которые у меня нет ответа

1. **Отдаёт ли каждый провайдер подтверждённую почту?** По VK ID это прямо поставлено вопросом
   в `02_SIMPASID.md` §2.7. От ответа зависит, насколько часто человек будет видеть экран C2.
2. **Нужен ли VK ID вообще?** Тот же §2.7 ставит это вопросом, а не данностью.
3. **Порядок кнопок на экране.** Сейчас реестр отдаёт их в фиксированном порядке
   `yandex, tid, sberid, vkid`. Задание 08 §4.1 запрещает выделять любой из них размером,
   цветом или порядком — но сам порядок кем-то задан быть должен.

## Яндекс: что уже готово (07.09.2026)

Адаптер написан и закрыт 26 тестами. Не хватает только ключей.

| Что | Состояние |
|---|---|
| Адреса Яндекса | взяты чтением `@auth/core/providers/yandex.js` — библиотеки, на которой работает вход в ПРАКТИКЕ: `oauth.yandex.ru/authorize`, `oauth.yandex.ru/token`, `login.yandex.ru/info` |
| Запрашиваемые права | `login:email login:info` — та же пара, что у ПРАКТИКИ. `login:avatar` **не запрашивается** |
| Что выходит из адаптера | ровно `subject`, `email`, `emailVerified`. ФИО, пол, день рождения, аватар и телефон выбрасываются немедленно — закрыто тестом |
| Redirect URI | `https://auth.cmpas.ru/callback/yandex` — маршрут реализован |
| Одноразовый `state` | таблица `provider_login_states`, только хешем, гасится при первом использовании |
| Занятый аккаунт провайдера | экран C3, вход не проходит |
| Провайдер без подтверждённой почты | экран C2, учётная запись **не заводится** |
| Ключи | `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET` в секретах репозитория. Половины недостаточно: провайдер не подключится, чтобы не показывать кнопку, ведущую в ошибку |

**Права на шаге 3 регистрации.** Из пяти «Основных» нужны две: адрес электронной почты и
«логин, имя и фамилия, пол». Вторая — только ради устойчивого идентификатора: почта меняется,
`id` нет. Дату рождения, портрет и номер телефона запрашивать нельзя — телефон прямо запрещён
И-2, аватар и ФИО названы в списке того, чего здесь не будет никогда. Человек видит запрошенные
права на экране согласия Яндекса, и лишнее там — это обещание, которое мы сами же нарушаем.

**НЕ ПРОВЕРЕНО:** отдаёт ли Яндекс признак подтверждения почты. Поля вроде `email_verified` в
разборе профиля `@auth/core` нет. Решение вынесено в одну константу
`YANDEX_EMAIL_IS_VERIFIED` в `services/providers/yandex.ts`: основной адрес считается
подтверждённым, потому что им управляет сам Яндекс. Окажется иначе — правится одно значение,
и все входы через Яндекс идут на экран C2. Способ проверки: документация Яндекс ID по составу
ответа `login.yandex.ru/info`.

## Что сделать, когда сведения появятся

Прислать по каждому провайдеру: есть ли договор, есть ли Android-SDK, отдаёт ли подтверждённую
почту, требования к кнопке. Секреты — сразу в `Settings → Secrets` репозитория `auth`,
именами `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` и так далее.

Дальше это отдельная задача с обычным порядком: тест до кода, `context7` перед утверждениями о
библиотеке провайдера, отчёт с расхождениями.
