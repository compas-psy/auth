## Шаг 0. Что обнаружено чтением, а не предположено

Репозиторий `github.com/compas-psy/cmpas.ru` склонирован на чтение 06.09.2026. Ниже —
фактические ответы на четыре вопроса плана.

### Чем деплоится

**SSH, не реестр образов.** `.github/workflows/deploy-docker.yml`:

* `appleboy/ssh-action@v1.0.3` с секретами `SERVER_HOST`, `SERVER_USER`, `SSH_PRIVATE_KEY`;
* на сервере выполняется `cd /var/www/cmpas.ru && git fetch origin main && git reset --hard
  origin/main`, затем `bash scripts/deploy-production-remote.sh`;
* образ **собирается на сервере** из исходников (`docker compose … --build`).

**Ни одного упоминания `ghcr.io`, `docker push` или реестра во всём каталоге
`.github/workflows/` нет** — проверено поиском. Сервер образы не тянет.

### Какой реверс-прокси и где его конфиги

**nginx на хосте**, вне Docker. Конфиги в `/etc/nginx/sites-available` + symlink в
`sites-enabled`, сертификаты `certbot --nginx`. Обнаружено по действующему прецеденту соседнего
поддомена: `sites/moments.cmpas.ru/deploy/moments.cmpas.ru.nginx.conf` и рядом с ним `SETUP.md`.
Приложение `cmpas.ru` публикует `3000:3000` и стоит за этим же nginx (в `docker-compose.yml`
соседа есть комментарий про ISPManager, зондировавший базу).

Боевой сервер: **45.144.30.190** — совпадает с A-записью `cmpas.ru`, которую я проверил
отдельно.

### Как на сервер попадают переменные окружения

Через `envs:` у `ssh-action`, дальше `scripts/deploy-production-remote.sh` функцией
`upsert_env` дописывает их в `/var/www/cmpas.ru/.env`. То есть **окружение живёт файлом на
сервере**, а секреты приезжают из `Settings → Secrets` репозитория.

### Куда монтируются тома

Именованные тома Docker: `db_data`, `mail_queue`, `uploaded_files`. Плюс host-mount
`/etc/ssl/ru-ca:ro`. Каталоги проектов на диске — `/var/www/cmpas.ru` и `/var/www/zapiski`.

**В `cmpas.ru` на этом шаге не изменено ничего.** Это была разведка.

### Следствие для человека

Вариант Б требует секретов деплоя — это то самое второе разовое действие, которое пакет заранее
назвал условным. Их **три**, и все три уже существуют в репозитории `cmpas.ru`:
`SERVER_HOST`, `SERVER_USER`, `SSH_PRIVATE_KEY`. Новых значений заводить не надо, надо скопировать
существующие в настройки репозитория `auth`.

Итого действий человека — **два**, оба из списка Р-3, третьего нет.

## Шаг 5. Правка в соседнем репозитории не понадобилась

План допускал PR в `cmpas.ru` для подключения compose-файла и блока прокси. **Он не нужен.**

Прецедент `moments.cmpas.ru` показал, что поддомен на этом сервере обслуживается отдельным
vhost, устанавливаемым отдельным workflow, и конфигурации `cmpas.ru` не касается вовсе.
Мы делаем так же, только файл vhost и workflow лежат в **нашем** репозитории:
`deploy/proxy/auth.cmpas.ru.conf` и `.github/workflows/provision.yml`.

Это лучше, чем PR: сосед не получает ни одного нового файла, и откат нашего контура не требует
трогать его репозиторий.

### Почему образ не собирался в самой сессии (пункт закрыт)

Сетевой шлюз этой сессии отвечает `403` на `CONNECT production.cloudfront.docker.com:443` —
то есть блоки образов Docker Hub недоступны по политике окружения, а не из-за ошибки в
`Dockerfile`. Это прямо отнесено окружением к тому, о чём следует сообщить, а не обходить.

**Как проверено:** задание `image` в `.github/workflows/build.yml` выполняет
`docker build --target runner .` на каждом push. В GitHub Actions Docker Hub доступен —
и 07.09.2026 сборка там прошла: `Образ собирается: success`. Единственное «не проверено»
Задачи 16 закрыто. Директива `# syntax=docker/dockerfile:1` из
`Dockerfile` убрана: она требует отдельного обращения к реестру, а никакого синтаксиса сверх
обычного файл не использует.

**Что в `Dockerfile` уже проверено косвенно:** все три сборки — портала, ресурса разработчика
и сервера — выполнены в этой сессии теми же командами (`npm ci`, `npm run build`) и прошли;
собранный портал отдаётся сервером, и это закрыто тестом `portal.serve.test.ts`.

## Урок, оплаченный красным прогоном

Первая выкладка упала на `Permission denied (publickey,password)`. Оба секрета были
непустыми — в логе они замаскированы как `***@***`, то есть значения подставились. Дело было
не в секретах, а в том, **как я подключался**: я написал подключение через голый `ssh` с
`printf` ключа в файл.

У соседа выкладка на **этот же сервер** **этими же тремя секретами** работает через
`appleboy/ssh-action@v1.0.3`, а обустройство `moments.cmpas.ru` — через
`appleboy/scp-action@v0.1.7`. Я это прочитал на Шаге 0 и всё равно написал своё.

Исправлено переходом на те же действия. Вывод шире одного случая: там, где на сервере уже
есть работающий способ, своя реализация должна иметь основание, а «так короче» основанием
не является.
