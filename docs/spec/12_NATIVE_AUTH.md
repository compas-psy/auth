# Нативный вход: мобильные приложения не уходят в браузер

Дополнение к `02_SIMPASID.md`, `08_AUTH_DESIGN_BRIEF.md` и плану Э2 · 06.09.2026 · версия 1.0
Решение учредителя: **мобильные приложения авторизуются исключительно по API.**

Этот документ разрешает конфликт между этим требованием и утверждённой архитектурой, задаёт
контур нативного входа и перечисляет, что из уже готового дизайна и плана меняется.

---

## 1. С чем именно конфликтует требование

Три места, и каждое надо назвать, а не обойти.

| Что утверждено сейчас | Где | Что требует переделки |
|---|---|---|
| «OIDC Authorization Code Flow + PKCE, обязательно для всех клиентов» | `02_SIMPASID.md` §6.1 | Authorization Code — это редирект в пользовательский агент. Для наших мобильных клиентов он заменяется первичным токен-API |
| Артборд **A5** — экран входа в Android Custom Tab | `08_AUTH_DESIGN_BRIEF.md` §4.2 | заменяется нативным экраном; Custom Tab исчезает |
| Артборды **O1, O2** — портал аккаунта мобильным вебом и в Custom Tab | `09_ACCOUNT_DESIGN_ADDENDUM.md` §5 | заменяются нативными экранами поверх того же API |

И одно место, которое **не** меняется: веб-продукты (ПРАКТИКА в браузере, ЗАПИСКИ на
десктопе) продолжают ходить через OIDC с редиректом. Требование касается мобильных
приложений, а не всего подряд.

---

## 2. Что «только по API» может значить, и что из этого делать нельзя

Требование однозначно для нашего собственного входа и неоднозначно для входа через чужого
провайдера. Разбираем отдельно, потому что цена ошибки разная.

### 2.1. Наш вход по почте — можно полностью по API

Сегодня вход по почте — это ссылка в письме. Ссылка открывается браузером: даже если
приложение перехватит её диплинком, человек уже вышел из приложения в почтовый клиент и
дальше в браузер.

**Решение: код из письма вместо ссылки — на мобильных.** Человек вводит почту в приложении,
получает письмо с шестизначным кодом, вводит код в приложении. Браузер не открывается ни
разу. На вебе ссылка остаётся: там она удобнее и там нет проблемы.

Это не новая сущность в схеме. Код — это тот же одноразовый секрет, что и токен ссылки, и
хранится он там же и так же: **только хешем**, в `magic_link_tokens.token_hash`. Отдельной
колонки `otp` не заводится — она прямо запрещена инвариантом И-2, и обходить его
переименованием нельзя, потому что запрет был про то, чтобы одноразовых секретов в открытом
виде в базе не появлялось.

**Цена решения, которую надо назвать.** Шестизначный код — это миллион вариантов, то есть на
несколько порядков меньше, чем 32 случайных байта в ссылке. Перебор становится реальной
угрозой, и её закрывают не длиной, а ограничениями:

* не больше **5 попыток** на один выпущенный код; на шестой запись гасится безвозвратно, и
  нужен новый код;
* время жизни **10 минут**, не 15;
* счётчик попыток живёт **на строке кода**, а не в памяти процесса и не в кэше;
* ограничитель на адрес и на устройство — тот же, что уже есть для ссылок (60 секунд);
* при исчерпании попыток ответ такой же по форме и по времени, как при неверном коде: разница
  в ответах — это оракул, который подсказывает перебирающему, что он на верном адресе.

Всё перечисленное проверяется тестом, а не декларируется.

### 2.2. Вход через Яндекс ID, T‑ID, Сбер ID, VK ID — «по API» имеет ровно один допустимый смысл

Здесь требование сталкивается с тем, что нельзя нарушать ни при каких обстоятельствах.

**Чего делать нельзя, и это не обсуждается:**

1. **Не показывать нативную форму логина провайдера внутри нашего приложения.** Приложение,
   собирающее пароль от Яндекса, — это ровно то, против чего был придуман OAuth. Кроме того,
   это прямо запрещено правилами самих провайдеров, и это готовая схема фишинга: человек не
   может отличить нашу форму от настоящей.
2. **Не открывать вход провайдера во встроенном webview.** Встроенный webview даёт
   приложению доступ к тому, что человек вводит, и к cookie сессии провайдера. Отраслевая
   норма для нативных приложений (RFC 8252) запрещает встроенные агенты именно поэтому.
3. **Не пересылать на сервер логин и пароль от провайдера ни в каком виде.**

**Что делать вместо — и это и есть «по API»:**

Использовать **нативный SDK провайдера**. У Яндекс ID, VK ID, T‑ID и Сбер ID есть Android-SDK
(**состав и возможности каждого не проверены** — проверяет агент по официальной документации
до реализации). SDK проводит авторизацию средствами самого провайдера — как правило, через
его установленное приложение — и возвращает нашему приложению код или токен провайдера.
Дальше приложение отправляет этот код **в наш API**, а сервер меняет его на личность и
выпускает наши токены.

```
Приложение ──SDK провайдера──▶ приложение провайдера
Приложение ──POST /v1/auth/provider/{provider}/native──▶ SimpasID
SimpasID   ──проверка кода на сервере провайдера──▶ провайдер
SimpasID   ──наши access и refresh──▶ приложение
```

Наш веб в этой схеме не открывается ни разу — требование выполнено. Но честно назвать надо и
следующее: **SDK провайдера может открыть окно самого провайдера**, если его приложение не
установлено. Это происходит в контуре провайдера, а не в нашем, и повлиять на это мы не можем.
Единственная альтернатива — не предлагать этого провайдера на мобильных вовсе.

**Отсюда правило, которое закрывает вопрос до появления данных:** провайдер показывается в
мобильном приложении **только если** у него есть нативный SDK, который мы подключили и
проверили. Нет SDK — провайдера на мобильном экране нет, и это не ошибка, а следствие
требования. Вход по коду из письма остаётся доступен всегда (И-5).

### 2.3. Портал аккаунта на мобильном — нативные экраны, тот же API

Портал аккаунта (профиль, почты, способы входа, устройства, коммуникации) в вебе остаётся
хостируемым разделом. В мобильном приложении те же самые экраны рисуются нативно и ходят в
**то же самое** публичное API v1.

Это не усложнение, а проверка правильности уже принятого решения: раз портал и продукты
работают одним API и внутреннего пути не существует, то мобильное приложение — просто ещё
один его потребитель. Если для нативного портала чего-то в API не хватает — это дефект API, а
не повод сделать исключение.

## 3. Контур первичного входа

### 3.1. Два входа в одну личность

| Клиент | Как входит | Почему так |
|---|---|---|
| ПРАКТИКА в браузере, ЗАПИСКИ на десктопе | OIDC Authorization Code + PKCE, редирект на `auth.cmpas.ru` | стандарт, уже утверждён, у веба есть браузер по определению |
| Наши мобильные приложения | первичный токен-API, без редиректов | требование учредителя |
| Любой сторонний клиент, если появится | **только OIDC**, первичный API ему недоступен | первичный API строит доверие на том, что клиент наш |

**Ключевое ограничение, без которого схема опасна:** первичный токен-API доступен **только
клиентам, помеченным в реестре как наши**. Клиент, не помеченный `first_party = true`,
получает `403` на всех маршрутах `/v1/auth/*` и обязан идти через OIDC. Это проверяется
тестом; забыть эту проверку — значит отдать всем желающим вход, спроектированный в расчёте на
доверенное приложение.

### 3.2. Маршруты первичного входа

```
POST /v1/auth/email/start
  { email, device_key, platform }
  → 202 { retry_after_seconds: 60 }          // всегда 202, даже если адреса нет

POST /v1/auth/email/verify
  { email, code, device_key }
  → 200 { access_token, refresh_token, expires_in, account }
  → 400 { error: "invalid_code", attempts_left }
  → 429 { error: "too_many_attempts" }        // код погашен, нужен новый

POST /v1/auth/provider/{provider}/native
  { provider_code | provider_token, device_key, platform }
  → 200 { access_token, refresh_token, expires_in, account }
  → 409 { error: "identity_taken" }
  → 422 { error: "email_required" }           // провайдер не отдал подтверждённую почту

POST /v1/auth/token/refresh
  { refresh_token }
  → 200 { access_token, refresh_token, expires_in }   // refresh всегда новый

POST /v1/auth/logout
  { refresh_token }
  → 204
```

Правила, каждое обязательно:

* **`POST /v1/auth/email/start` всегда отвечает 202**, независимо от того, есть ли такой
  аккаунт. Разные ответы превращают ручку в способ узнать, зарегистрирован ли человек в
  сервисе для психологической помощи.
* **Ротация refresh при каждом использовании.** Мобильное приложение — публичный клиент,
  секрета у него нет и быть не может: всё, что зашито в APK, извлекается. Поэтому
  безопасность держится не на секрете, а на том, что refresh одноразовый.
* **Обнаружение повторного использования.** Если пришёл уже потраченный refresh — вся цепочка
  токенов этого устройства гасится, и человеку нужен новый вход. Это стандартная реакция на
  украденный токен, и она обязана быть, иначе ротация бессмысленна.
* **Привязка к устройству.** `device_key` сохраняется с сессией и показывается в списке
  «Устройства и сеансы». Отзыв сеанса из портала немедленно убивает refresh.
* **`422 email_required`** ведёт на нативный экран запроса почты — это И-5 в мобильном
  исполнении: у учётной записи всегда есть подтверждённая почта.

### 3.3. Чего в первичном API нет и не появится

Пароля. Телефона. SMS. Кода по SMS. Формы логина провайдера. Возможности передать чужой
`account_id`. Возможности для стороннего клиента выпустить токен на пользователя.

## 4. Что меняется в дизайне

Артборды заменяются, а не дополняются. Дизайн-система, тексты и юридическая конструкция
остаются прежними — меняется только то, где эти экраны живут.

| Было | Стало | Примечание |
|---|---|---|
| **A5** — вход в Android Custom Tab | **A5н** — нативный экран входа: те же кнопки провайдеров, тот же разделитель, то же поле почты, та же юридическая строка. Рамки браузера и адресной строки нет | состав провайдеров приходит из `GET /v1/auth/methods` с учётом платформы: на мобильном показываются только те, у кого подключён SDK |
| — | **A6н** — ввод кода из письма: шесть ячеек, счётчик попыток, «Отправить снова» с паузой 60 секунд | заменяет B2 на мобильном; на вебе B2 остаётся как есть |
| — | **A7н** — «Нужна электронная почта» после провайдера, не отдавшего подтверждённый адрес | нативный аналог C2 |
| **O1** — портал аккаунта мобильным вебом | **O1н** — нативные экраны портала: обзор, личные данные, безопасность, устройства, коммуникации | те же тексты, тот же состав, тот же API |
| **O2** — коммуникации в Custom Tab | **O2н** — нативный экран коммуникаций | переключатели выключены по умолчанию, «Отключить всю рекламу» на месте |

**Юридическая конструкция на нативных экранах не смягчается.** Акцепт действием — кнопкой
входа; отдельная строка про принимаемое соглашение с указанием редакции; Политика ссылкой без
глагола принятия; ссылки открываются во внешнем браузере, потому что это чтение документа, а
не ввод данных. Обязательных чекбоксов нет.

**Одна вещь, которую нельзя потерять при переходе на нативный экран:** строка «Провайдер
увидит, что вы вошли в СИМПАС, и когда». На мобильном она нужнее, чем в вебе: там кнопка
провайдера ведёт в его собственное приложение, и ощущение «это всё одно и то же» сильнее.

## 5. Что меняется в плане Э2

Добавляются четыре задачи. Нумерация отдельная, чтобы не сдвигать уже написанные.

| Задача | Что | После какой задачи |
|---|---|---|
| **Н1** | Первичный токен-API: выпуск, ротация refresh, обнаружение повторного использования, отзыв, флаг `first_party` в реестре клиентов | после Задачи 7 |
| **Н2** | Вход по коду из письма: выпуск, проверка, счётчик попыток на строке, гашение после пятой | после Н1 |
| **Н3** | Обмен нативного кода провайдера на наши токены; отдельно по каждому провайдеру, у которого проверен SDK | после Н2 |
| **Н4** | Полнота API для нативного портала: пройти каждый экран O1н и убедиться, что всё делается существующими ручками; недостающее добавить в спецификацию **до** реализации | после Задачи 13 |

К приёмке Э2 добавляются критерии:

1. Мобильный сценарий входа по почте проходится **без единого выхода в браузер** — проверяется
   на устройстве, с записью.
2. Сторонний клиент (не `first_party`) получает `403` на `/v1/auth/*`.
3. Повторное использование refresh гасит цепочку и требует нового входа.
4. Исчерпание попыток кода гасит код; ответы при неверном коде и при исчерпании неразличимы по
   форме и по времени.
5. Ни в одном мобильном продукте нет встроенного webview для входа — проверяется поиском по
   коду продукта.
6. `GET /v1/auth/methods` на мобильной платформе не возвращает провайдера без подключённого
   SDK.

## 6. Что проверяет человек, а не агент

* **Наличие и условия Android-SDK** у Яндекс ID, T‑ID, Сбер ID и VK ID: сам факт, требования к
  подключению, требования к виду кнопки в нативном приложении, ограничения по типам приложений.
  Все четыре — **не проверено**.
* **Позволяют ли правила провайдера** нашу схему «SDK отдаёт код приложению → код уходит на наш
  сервер → сервер меняет его на личность». Схема стандартная, но у конкретного провайдера могут
  быть условия.
* **iOS.** В этом документе описан Android, потому что он есть в портфеле. Состояние iOS
  **не проверено**; при появлении — та же схема с системным механизмом платформы.

---

## 7. Чего не делать

1. **Не показывать форму логина провайдера в нашем приложении** ни в каком виде.
2. **Не открывать вход провайдера во встроенном webview.**
3. **Не хранить и не пересылать учётные данные провайдера.**
4. **Не открывать первичный токен-API сторонним клиентам** — им OIDC.
5. **Не заводить колонку `otp`** и вообще не хранить одноразовые секреты иначе как хешем
   (И-2).
6. **Не удлинять жизнь кода и не увеличивать число попыток** «ради удобства»: это прямая
   уступка перебору.
7. **Не отвечать по-разному** на «такого адреса нет» и «письмо отправлено».
8. **Не считать нативный вход поводом смягчить юридическую конструкцию.** Акцепт действием,
   редакция названа, Политика не принимается.
