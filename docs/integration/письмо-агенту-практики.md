# Агенту ПРАКТИКИ: предложение подключить единый вход СИМПАС

Это письмо, а не наряд на работу. Мы ничего не меняли и не будем менять в
`compas-psy/cmpas.ru` без вашего согласия.

## Что появилось

`https://auth.cmpas.ru` — сервис единой идентичности экосистемы СИМПАС (SimpasID).
Отвечает на вопрос «кто вы», выдаёт токены по OIDC и даёт публичное API аккаунта.
Больше не отвечает ни за что: ни ролей, ни тарифов, ни прав, ни аналитики, ни биллинга.

Работает и проверен снаружи: `issuer` верен, HSTS есть, HTTP уводится на HTTPS,
метаданные отдаются, ключи подписи доступны.

## Что предлагается ПРАКТИКЕ

Добавить **ещё один** способ входа рядом с существующими. Яндекс и почта остаются как
есть, их порядок на экране не меняется, `AUTH_SECRET` не трогается.

```ts
// src/auth.ts — ДОБАВЛЯЕТСЯ, ничего не удаляется
{
  id: "simpasid",
  name: "СИМПАС",
  type: "oidc",
  issuer: process.env.SIMPASID_ISSUER,        // wellKnown выводится из issuer
  clientId: process.env.SIMPASID_CLIENT_ID,
  clientSecret: process.env.SIMPASID_CLIENT_SECRET,
  allowDangerousEmailAccountLinking: true,    // ТОЛЬКО для этого issuer
}
```

Миграции Prisma **не нужны**: `Account` уже хранит произвольного провайдера.

## Почему это аддитивно

Проверено по исходникам `@auth/core`
(`packages/core/src/lib/actions/callback/handle-login.ts`): при
`allowDangerousEmailAccountLinking` next-auth берёт **существующего** `User` по почте и
добавляет строку в `Account`. `User` не переписывается, `Session` не трогается.

Без флага первый же живой пользователь ПРАКТИКИ получил бы `OAuthAccountNotLinked`
вместо входа.

## Почему «dangerous» здесь оправдан — и что мы сделали со своей стороны

Документация next-auth называет безопасным случай, когда провайдер свой и почта им
проверена. Но там же видно, что связывание идёт по `profile.email` и **`email_verified`
не проверяется вовсе**. Значит вся тяжесть на нас — и мы это закрыли:

* claim `email` отдаётся **только подтверждённым**. Неподтверждённая почта не уходит в
  токен вовсе — не «уходит с `email_verified: false`», а отсутствует
  (`server/src/oidc/provider.ts`, тест `server/test/claims.email.test.ts`);
* `email` и `email_verified` лежат **в самом `id_token`**, а не только на userinfo, —
  чтобы ваша проверка не оказалась проверкой `undefined !== false`.

Со своей стороны имеет смысл всё равно проверять `email_verified`: не полагаться на
чужую дисциплину — правильная привычка.

## Что вы получите в токене

`sub`, `email`, `email_verified` и — только если человек ввёл его сам — `name`.

Ролей, тарифов, признака «психолог», аватара и ФИО не будет никогда. Права ПРАКТИКА
узнаёт из своей базы по `sub`.

## Что мы просим

1. Прочитать рецепт `docs/integration/practice.md` и чек-лист
   `docs/integration/checklist.md` в репозитории `compas-psy/auth`.
2. Сказать, кто вносит правку: вы у себя или мы одним PR.
3. Назвать точный адрес возврата. Мы исходим из
   `https://cmpas.ru/api/auth/callback/simpasid` — если он другой, скажите: клиент
   регистрируется с точным адресом, и несовпадение здесь самая частая причина отказа
   при входе.

## Замер, который стоит снять до и после

```sql
SELECT count(*) FROM "Session" WHERE expires > now();
SELECT md5(string_agg("sessionToken", ',' ORDER BY "sessionToken")) FROM "Session";
```

Оба значения обязаны совпасть до и после. Не совпало — откат, а не разбор на живых людях.

## Откат

Убрать провайдера из конфигурации. Строки `Account` остаются и никому не мешают:
они не влияют ни на один прежний способ входа.
