# Вход СИМПАС в мобильной ПРАКТИКЕ

Рецепт для приложения `android/` репозитория `github.com/compas-psy/cmpas.ru`.
Веб-часть переезжает иначе — см. `practice.md`; здесь другой протокол, а не другой
синтаксис.

**Что этот шаг делает:** добавляет вход СИМПАС рядом с действующими.
**Чего он не делает:** не выключает вход по ссылке из письма, не трогает
`UserPreferences`, не меняет `AuthInterceptor` и не касается базы ПРАКТИКИ.

## Почему на мобильном не OIDC с редиректом

Требование СИМПАС (`docs/spec/12_NATIVE_AUTH.md`): вход в наших приложениях идёт
**первичным токен-API**, без ухода в браузер. Ни Custom Tab, ни мобильный веб, ни
редирект в наш веб. Внутри приложения нет ни формы логина провайдера, ни webview —
приложение, собирающее пароль от Яндекса, это готовая схема фишинга, и именно против
неё придуман OAuth.

Порядок такой: нативный SDK провайдера отдаёт приложению код → приложение отдаёт код
нам → сервер меняет его на личность. Провайдер, у которого подключённого нативного SDK
нет, на мобильном экране **не показывается**; это следствие требования, а не ошибка.

Вход по почте на мобильном — **код из письма**, а не ссылка: ссылка уводит человека в
почтовый клиент и браузер, откуда в приложение он не возвращается.

## Что в приложении сейчас

Прочитано 07.09.2026, ветка по умолчанию, коммит `326d72b`:

| Что | Где | Как сейчас |
|---|---|---|
| экран входа | `presentation/auth/LoginScreen.kt` | кнопка «Войти через Яндекс» и поле почты |
| вход через Яндекс | там же, `onYandexLogin` | `Intent.ACTION_VIEW` на `oauth.yandex.ru` — **уход в системный браузер** |
| вход по почте | `presentation/auth/LoginViewModel.kt` | `requestMagicLink`, шаг `CHECK_EMAIL` — **ссылка**, не код |
| сеть | `di/NetworkModule.kt` | один `OkHttpClient` на всё приложение, Retrofit, kotlinx-serialization |
| токены | `data/api/AuthInterceptor.kt` | Bearer на каждый запрос, обновление на `cmpas.ru/api/mobile/auth/refresh` |
| хранение токенов | `data/datastore/UserPreferences.kt` | обычный `Preferences DataStore` (`compas_prefs`) — **без шифрования и без Keystore** |

Оба действующих способа входа расходятся с требованием СИМПАС: первый уходит в браузер,
второй присылает ссылку. **Дырой в безопасности это не является** — переход в системный
браузер безопаснее webview, а ссылка в письме не хуже кода. Это расхождение с
требованием, и решать его — не задача этого рецепта.

## Шаг 1. Подключить клиента

Библиотека лежит в `clients/android` репозитория `compas-psy/auth`. Чистый Kotlin/JVM,
без зависимостей от Android: проверяется обычными тестами на JVM, а не эмулятором.
Зависимости — OkHttp 4 и kotlinx-serialization, обе у ПРАКТИКИ уже стоят.

```kotlin
// android/app/build.gradle.kts
implementation(project(":simpasid-client"))   // или maven-координаты, когда появятся
```

## Шаг 2. Отдельный OkHttpClient — не общий

**Это единственное место, где ошибка стоит дорого.**

`NetworkModule.provideOkHttpClient` отдаёт один клиент на всё приложение, а его
`AuthInterceptor` вешает `Authorization: Bearer <ключ ПРАКТИКИ>` на **каждый** запрос
и в отладочной сборке печатает тела целиком (`HttpLoggingInterceptor.Level.BODY`).
Передать этот клиент сюда значит:

* отправить ключ доступа ПРАКТИКИ на `auth.cmpas.ru` — службе, которая его не просила;
* напечатать код из письма и токен обновления в журнал устройства.

Поэтому `SimpasIdClient` **снимает перехватчики** с переданного клиента: таймауты, пул
соединений, закрепление сертификата и прокси наследуются, перехватчики — нет. Это
проверено тестом, а не обещано. Но полагаться на это не нужно — дайте ему свой:

```kotlin
@Provides @Singleton @SimpasId
fun provideSimpasHttp(): OkHttpClient = OkHttpClient.Builder()
    .connectTimeout(30, TimeUnit.SECONDS)
    .build()

@Provides @Singleton
fun provideSimpasId(@SimpasId http: OkHttpClient) = SimpasIdClient(
    baseUrl = "https://auth.cmpas.ru",
    clientId = BuildConfig.SIMPASID_CLIENT_ID,   // practice-mobile
    http = http,
)
```

## Шаг 3. Вход по коду из письма

```kotlin
val pause = simpasId.startEmailAuth(
    email = email, deviceKey = deviceKey, platform = Platform.ANDROID,
    termsVersion = "0.9",
)
// Ответ ОДИНАКОВ независимо от того, есть ли такая учётная запись: разные
// ответы превратили бы экран входа в способ узнать, зарегистрирован ли
// человек в сервисе психологической помощи. Показывать «мы отправили код,
// если такой адрес у нас есть» — так и надо.

val tokens = simpasId.verifyEmailAuth(email, code, deviceKey, Platform.ANDROID)
// tokens.accessToken, tokens.refreshToken, tokens.account.id — это sub.
```

`deviceKey` — постоянный для установки случайный идентификатор, который заводит
приложение. Ни IMEI, ни ANDROID_ID, ни рекламный идентификатор: они переживают
переустановку и опознают человека, а не установку.

## Шаг 4. Вход через Яндекс — только нативным SDK

`simpasId.exchangeProviderCode("yandex", кодОтSDK, deviceKey, Platform.ANDROID)`.

Код берётся у **нативного** Yandex Login SDK. Действующий переход в браузер
(`Intent.ACTION_VIEW`) сюда не годится: он возвращает код на веб-адрес ПРАКТИКИ, а не
приложению.

Пока нативный SDK не подключён, `simpasId.authMethods(Platform.ANDROID)` вернёт список без
`yandex` — и кнопки на экране быть не должно. Список берётся у сервера, а не
задаётся в приложении.

## Шаг 5. Хранение токенов

В библиотеку **не входит намеренно**. Библиотека, знающая про хранилище, навязала
бы своё, а ошибка в хранении ключа входа дороже удобства. Куда класть — решение
приложения.

Рекомендация: `EncryptedSharedPreferences` поверх Keystore.

**Сегодня это не так, и рецепт не должен делать вид, что так.** Токены лежат в
обычном `Preferences DataStore` (`data/datastore/UserPreferences.kt`, хранилище
`compas_prefs`), без шифрования и без Keystore — сообщено агентом ПРАКТИКИ
07.09.2026 (issue `compas-psy/cmpas.ru#132`) и в рецепт вписано, потому что
предыдущая редакция исходила из невыполненного предположения.

На устройстве без root это не открытая дверь: песочница приложения защищает файл.
Но наш клиент **не полагается** на то, что за хранилищем стоит Keystore, и не будет:
предположение, которое может оказаться ложным молча, — не защита.

Токен обновления **одноразовый**: повторное использование сервер считает кражей и
гасит всю цепочку. Хранить нужно только последний выданный.

## Шаг 6. Что говорит человек и чего он не видит

Человек видит «Аккаунт СИМПАС», «способы входа», «устройства и сеансы», «ключ
доступа». Он **никогда** не видит слов «OAuth», «токен», «OIDC», «провайдер
идентичности», «SimpasID», «сессия» в техническом значении.

## Шаг 7. Юридическая половина экрана

Разбор снимка экрана от 11.09.2026. Технически шаги 1–5 меняют, **как** приложение
опознаёт человека; этот шаг меняет, **что человек при этом принимает**. Источник —
`docs/spec/14_LEGAL_PRODUCTS_UNIFIED.md` и пакет макетов от 11.09.2026
(`docs/design/АККАУНТ_ВО_ВСЕХ_ПРОДУКТАХ.md`).

### Что на экране не так сейчас

| Что видно | Чем это плохо |
|---|---|
| кнопка «Войти через Яндекс» | ПРАКТИКА опознаёт человека сама, мимо СИМПАС. После переезда своих кнопок провайдеров у продукта нет (§1 ТЗ) |
| поле Email и «Войти по email» | своя форма входа и своя магическая ссылка. Там же §1 |
| «30 дней бесплатно · Без привязки карты» на месте юридической строки | акцепта нет вовсе: человек создаёт учётную запись, ничего не принимая |

### Где что принимается теперь

Разделение жёсткое, и оно снимает половину работы с ПРАКТИКИ:

| Где | Что |
|---|---|
| **в СИМПАС**, на экране входа | Пользовательское соглашение Экосистемы — один раз, при создании аккаунта |
| **в СИМПАС**, в аккаунте | согласие на рекламу — добровольно, по каналам |
| **в ПРАКТИКЕ**, при первом подключении | Особые условия ПРАКТИКИ |
| **в ПРАКТИКЕ**, при активации проф. профиля | Профессиональное соглашение |
| **в ПРАКТИКЕ**, перед первым клиентом | заверение психолога как оператора данных |

**Продукт не принимает центральные документы.** Человек, дошедший до ПРАКТИКИ, уже принял
Пользовательское соглашение — в СИМПАС. Повторный акцепт в продукте создаёт вторую запись
о том же факте с другим временем и другим источником, и в споре придётся объяснять, какая
из них настоящая.

Поэтому на экране входа ПРАКТИКИ юридической строки про Соглашение и Политику **быть не
должно**. Она уходит к нам. Вместо неё у ПРАКТИКИ появляется то, чего сейчас нет нигде:
экран первого подключения сервиса.

### Экран первого подключения

Показывается один раз, при первом подключении ПРАКТИКИ этим человеком. Не при входе, не
при обновлении, не «на всякий случай».

> Начиная работу, вы принимаете Особые условия ПРАКТИКИ, редакция 1.0.

Ссылка ведёт на **конкретную редакцию**: `https://auth.cmpas.ru/legal/practice-terms/{версия}`.

Номер редакции и адрес берутся у сервера — `GET /v1/legal/documents`, в котлин-клиенте
это `legalDocuments()`. Вписывать номер в приложение руками нельзя: он меняется без
выпуска новой сборки, и вписанный однажды покажет человеку не ту редакцию, которую он
принимает.

Нужная строка — та, у которой `product == "practice"`. Если её в ответе нет, значит
Особые условия сервиса не опубликованы, и подключать нечего: показывать экран
подключения в этом случае запрещено.

Акцепт отправляется обратно: `PUT /v1/account/consents` с `document_code`, `version`
(ровно та, что показана на экране), `status: "granted"` и `action` — именем действия,
которым человек это выразил. Сервер отвергнет расхождение версий кодом `409
stale_document_version`: это защита от акцепта на редакцию, которой человек не видел.
Своего хранения акцепта заводить не нужно.

Кнопка — **содержательная**: «Начать работу в ПРАКТИКЕ», а не «Принять». Кнопка «Принять»
превращает экран в формальность, которую пролистывают; кнопка с именем действия и есть
акцепт действием.

Обязательного чекбокса нет. Предустановленных галочек нет нигде.

### Четыре правила, нарушение любого блокирует приёмку

1. Обязательного чекбокса нет — акцепт даётся действием, содержательной кнопкой.
2. Юридическая строка стоит под всем блоком, а не под одной кнопкой.
3. Политика упоминается **без глагола принятия**: это информационный документ.
4. Ссылки ведут на конкретную редакцию, а не на текущую. В карточке уже принятого
   документа — на ту редакцию, которую человек принял.

Образец, с которого это списывается, — наш собственный экран входа:
`portal/src/screens/SignIn.tsx`, блок `data-testid="legal-line"`.

### Единственный обязательный чекбокс во всей Экосистеме

Заверение психолога перед **первым** созданием или импортом карточки клиента.
Формулировка дословная, переписывать запрещено:

> Я подтверждаю, что являюсь оператором персональных данных своих клиентов и располагаю
> необходимыми правовыми основаниями для их обработки и передачи ПРАКТИКЕ для обработки по
> моему поручению.

Кнопка неактивна, пока галка не поставлена. Галка не предустановлена. Повторно при каждом
клиенте не спрашивается — только если изменилась формулировка.

### Чего у ПРАКТИКИ не может быть

Своего пользовательского соглашения. Своей политики конфиденциальности — политика это
документ оператора, а оператор один. Своего рекламного согласия и своих настроек рассылок.
**Своей копии текста любого документа**: продукт ссылается на адрес в консент-центре, копия
в репозитории продукта через полгода разойдётся с реестром.

Собственные страницы соглашения и политики на `cmpas.ru` снимаются — их содержательная
часть переезжает разделом внутрь Особых условий ПРАКТИКИ.

### Знак СИМПАС

Ставится как есть, не перекрашивается и не перерисовывается ни в одной теме: это знак
владельца аккаунта, а не элемент интерфейса. Канонический файл —
`https://auth.cmpas.ru/assets/brand/simpas-logo-disc.svg`. Возьмите его оттуда копией в
свой репозиторий: тянуть его на каждый показ значит уронить свой экран вместе с нашим
сервисом.

### Четыре состояния, которые обязаны существовать

1. **Единый вход недоступен** — дословно: «Вход временно недоступен. Мы уже чиним.
   Попробуйте через несколько минут.» Ни кода ошибки, ни адреса сервера на экране.
2. **Вход истёк** — плашка, а не экран и не модалка: ПРАКТИКА живёт своей сессией и из
   приложения никого не выкидывает.
3. **Ждём ответа** — пока идёт обмен кода на личность.
4. **Подтверждение выхода** — с указанием, что останется на устройстве. Выход из ПРАКТИКИ
   не выходит из аккаунта СИМПАС и не трогает другие приложения.

## Чего этот рецепт не решает

Что делать с действующими способами входа — оставить рядом, заменить или выключить.
Это решение агента ПРАКТИКИ и учредителя, а не наше. Принцип аддитивности требует
только одного: живой пользователь не должен заметить, что мы что-то меняли.
