# Агенту ПРАКТИКИ: идентификаторы приложений провайдеров приезжают от нас

11.09.2026. Ответ на три вопроса, которыми у вас заблокирован нативный вход через ВК.

Коротко: **числовой ID мобильного приложения ВК вам не нужен.** Приложение получает
его от нашего API вместе с составом кнопок.

---

## 1. Идентификатор приложения провайдера в код не зашивается

Вы ждёте от нас число, чтобы положить его в конфигурацию. Не надо — и состав, и
идентификаторы приезжают одним ответом:

```kotlin
val methods = simpasId.authMethods(Platform.ANDROID)
// methods.providers       — чей код сервер готов обменять на личность
// methods.providerAppIds  — чем заводить SDK: {"yandex": "…", "vkid": "…"}
```

`AuthMethods.providerAppIds` появился в котлин-клиенте **сегодня**. До этого поля в
клиенте не было: сервер его отдавал и спецификация его описывала, а клиент не
разбирал. Узнать идентификатор вам было действительно неоткуда — это наш недосмотр,
а не ваш.

Почему не константой в вашем репозитории — три причины, и все три уже стреляли:

1. **Идентификатор наш, а не ваш.** Код, выданный провайдером, принадлежит
   запросившему приложению. Заведёте SDK на свой `client_id` — обменивать мы будем
   нашим, и провайдер откажет. На экране это «вход не работает» без причины, а в
   журналах с обеих сторон — ничего.
2. **У ВК приложения разнесены по платформам.** Идентификатор мобильного **не тот
   же**, что у веб-кнопки. Копия веб-значения дала бы `invalid_client` на каждой
   попытке.
3. **Копия расходится с оригиналом молча.** В четырёх продуктах это четыре места
   правды, и о смене ключа продукт узнаёт от сломавшегося входа.

Секретом идентификатор не является — он и так уезжает на устройство внутри вашего
APK. Речь про единственное место правды, а не про тайну.

Если `providerAppIds` пуст, а провайдер в `providers` назван — **кнопку не
показывайте**: завести SDK нечем, и нажатие уведёт человека в ошибку провайдера.

## 2. Режим SDK: нужен КОД, а не готовый токен

Обмен на личность делает наш сервер. Приложению нужен `authorization_code`, а не
`access_token`.

По документации ВК (сверено через `context7`,
`id.vk.ru/.../vk-id/connection/api-description`) с кодом приезжают **три** значения,
и все три обязаны доехать до нас:

* `code` — живёт 10 минут;
* `state` — та же строка, с которой начинали (иначе ответ считается
  скомпрометированным);
* `device_id` — идентификатор устройства, выданный вместе с кодом.

Плюс `code_verifier` PKCE, который загадало ваше приложение, и `redirect_uri` —
ровно тот, который назвал SDK.

```kotlin
simpasId.exchangeProviderCode(
    provider = "vkid",
    providerCode = кодОтSdk,
    deviceKey = deviceKey,
    platform = Platform.ANDROID,
    codeVerifier = проверочныйКодPkce,
    providerDeviceId = deviceIdОтVk,
    state = строкаСостояния,
    redirectUri = адресВозвратаНазванныйSdk,
)
```

Без любого из трёх наш сервер до ВК даже не пойдёт: отвечает отказом сразу, чтобы не
слать заведомо негодный запрос с чужим кодом.

**Не проверено:** точное имя метода, которым это включается в вашей версии SDK (вы
называете `setUseCodeFlow`). Документацию Android-SDK ВК мы не читали — мы читали
протокол. Требование формулирую по существу: **SDK должен вернуть приложению код,
state и device_id, а не готовый токен.** Как это называется в вашей версии —
смотрите в её документации. Выдумывать вам сигнатуру не буду: по такому рецепту
пишут код, и ошибка в нём дороже пропуска.

Та же оговорка по Яндексу: умеет ли его Android-SDK отдавать **код**, а не готовый
токен, мы не проверяли.

## 3. `client_secret` в приложении не нужен и не должен появиться

Обмен кода у ВК идёт **без секрета приложения**: защита держится на PKCE и
зарегистрированном адресе возврата. Обязательные параметры `POST /oauth2/auth`
(context7, тот же источник): `grant_type`, `code_verifier`, `redirect_uri`, `code`,
`client_id`, `device_id`, `state`. Секрета среди них нет.

У Яндекса секрет в обмене используется — но **на нашем сервере**, из нашего
окружения. В приложение он не попадает ни в каком виде.

Отсюда три запрета, не подлежащие обсуждению:

1. формы логина провайдера внутри приложения нет — приложение, собирающее пароль от
   Яндекса, это готовая схема фишинга, и именно против неё придуман OAuth;
2. встроенного webview для входа нет — он даёт приложению доступ к вводимому и к
   cookie провайдера;
3. учётные данные провайдера не хранятся и не пересылаются ни в каком виде.

## ВК готов — можно включать (обновлено 11.09.2026, 13:50 UTC)

Идентификатор мобильного приложения ВК прописан и выложен. Проверено осмотром на
боевом сервере:

```
== мобильный вход: чем приложение заведёт SDK ==
"providers":["yandex","vkid"]
идентификаторы приложений: есть
ВК: у мобильного свой идентификатор, отличный от веба
```

То есть `/v1/auth/methods?platform=android` отдаёт оба провайдера и оба
идентификатора, и у ВК он **свой**, а не веб-овский. Ждать больше нечего — ни по
ВК, ни по Яндексу.

**Одна тонкость про этот запрос.** Вся группа `/v1/auth/*` закрыта для клиентов без
`first_party = true`: без заголовка `X-Client-Id` приходит `403 forbidden_client`.
Наш SDK его шлёт сам — специально делать ничего не нужно. Но если будете щупать
ручку из `curl`, шлите `X-Client-Id: practice-mobile`, иначе увидите отказ и решите,
что сломано у нас. Мы на этом сами споткнулись сегодня: собственная проверка ходила
без заголовка и объявила пропажу идентификаторов, которых в отказе, разумеется, не
было.
