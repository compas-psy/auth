# Переезд ПРАКТИКИ на единый вход

Стек проверен чтением `github.com/compas-psy/cmpas.ru` 06.09.2026:
`next-auth ^5.0.0-beta.30`, `@auth/prisma-adapter`, `prisma 5.22.0`, Next.js 16.1.1,
`session.strategy = "database"`, действующие способы входа — Яндекс и почта (`src/auth.ts`).

**Что этот шаг делает:** добавляет ещё один способ входа рядом с существующими.
**Чего он не делает:** не меняет `AUTH_SECRET`, не трогает строки `User`, `Account`, `Session`,
не выключает прежние способы входа и не меняет их порядок на экране.

> свой код и нашёл три вещи, которых в рецепте не было. Записаны здесь,
> чтобы следующий читатель не повторил ошибку.
>

>    строит список провайдеров — кнопки заданы вручную. PR, меняющий

## Шаг 1. Провайдер добавляется, ничего не удаляется

<!-- блок auth-config -->
```ts
// src/auth.ts — ДОБАВЛЯЕТСЯ провайдер, ничего не удаляется
providers: [
  Yandex({ /* как было */ }),
  Nodemailer({ /* как было */ }),
  {
    id: "simpasid",
    name: "СИМПАС",
    type: "oidc",
    issuer: process.env.SIMPASID_ISSUER,      // wellKnown выводится из issuer
    clientId: process.env.SIMPASID_CLIENT_ID,
    clientSecret: process.env.SIMPASID_CLIENT_SECRET,
    allowDangerousEmailAccountLinking: true,  // ТОЛЬКО для нашего issuer
  },
],
```

Адрес обратного вызова: `https://cmpas.ru/api/auth/callback/simpasid`.

**Почему `wellKnown` не задаётся.** Проверено через `context7`
(`packages/core/src/lib/utils/providers.ts`): если задан `issuer`, `next-auth` сам выводит
`wellKnown` как `{issuer}/.well-known/openid-configuration`. Сервис отвечает по этому адресу —
это отдельно закреплено тестом на нашей стороне, потому что иначе рецепт молча перестал бы
работать.

**Почему `allowDangerousEmailAccountLinking` включается и почему это не безрассудство.**
Проверено через `context7` (`packages/core/src/lib/actions/callback/handle-login.ts`): без него
`next-auth` бросает `OAuthAccountNotLinked`, когда учётная запись с такой почтой уже есть, — то
есть живой пользователь ПРАКТИКИ при первом входе через СИМПАС получил бы ошибку вместо входа.
Флаг доверяет провайдеру проверку почты. Мы имеем право доверять **своему** issuer: у нас почта
подтверждается переходом по ссылке или кодом из письма, и неподтверждённая почта входа не даёт.
Ставить этот флаг любому другому провайдеру нельзя.

## Шаг 2. Переменные окружения

```
SIMPASID_ISSUER=https://auth.cmpas.ru
SIMPASID_CLIENT_ID=practice-web
SIMPASID_CLIENT_SECRET=<выдаётся один раз при регистрации клиента>
```

Для стенда — **отдельный клиент**, а не `localhost` в боевом:

```
SIMPASID_CLIENT_ID=practice-dev     # адрес возврата http://localhost:3000/...
SIMPASID_CLIENT_SECRET=<свой, отдельный>
```

`AUTH_SECRET` **не трогается**. Смена этого значения инвалидирует все сессии — в самом
`src/auth.ts` соседнего репозитория на этот счёт стоит предупреждение и проверка.

## Шаг 3. Что произойдёт с существующими пользователями

| Кто | Что увидит |
|---|---|
| Вошёл раньше, сессия жива | ничего. `strategy: "database"` — строка `Session` не тронута |
| Входит прежним способом | всё как было: Яндекс и почта на месте |
| Входит через СИМПАС впервые, почта совпадает | попадает в **свою** учётную запись; добавляется строка `Account(provider="simpasid")` |
| Входит через СИМПАС, почты в базе нет | заводится новая учётная запись — как при любом первом входе |

`User.id` остаётся первичным ключом всех данных продукта. СИМПАС его не переписывает: связь
идёт строкой в `product_links` на нашей стороне и строкой `Account` на стороне ПРАКТИКИ.

## Шаг 4а. Две подсказки: какой кружок нажали и какой адрес набрали

Обе необязательны, обе ничего не пропускают и не подтверждают. Негодное значение
игнорируется молча: опечатка в чужой ссылке не должна оборачиваться отказом входа.

### `provider` — какой кружок нажал человек

```ts
signIn("simpasid", { callbackUrl }, { provider: "yandex" })  // или "vkid"
```

Названный провайдер встаёт на нашем экране первым и помечен. Значение — код из
`GET /v1/auth/methods`; неизвестное или неподключённое не выделяет никого.

**Чего подсказка НЕ делает: не уводит человека прямо к провайдеру.** Он увидит наш
экран и нажмёт второй раз. Это не недоделка, а требование: Пользовательское
соглашение принимается действием на нашем экране и больше нигде — уведи мы человека
сразу к провайдеру, брать акцепт стало бы негде.

### `login_hint` — какой адрес человек уже набрал

```ts
signIn("simpasid", { callbackUrl }, { login_hint: email })
```

Штатный параметр спецификации OIDC. Адрес подставляется в поле нашего экрана, и на
этом всё: стереть и набрать другой можно в любой момент, а вход по-прежнему
подтверждается письмом в этот ящик.

Нужен он ровно для одного: чтобы у продукта со своим полем почты не было причины
держать **свою** форму входа. Учётная запись, заведённая мимо нашего экрана, заведена
мимо акцепта Соглашения, и записать его потом будет негде — в СИМПАС такого человека
не существует.

Подставленный адрес ничего не подтверждает, поэтому параметром можно безопасно
пользоваться из ссылки. Ответ сервиса на «есть такой адрес или нет» одинаков в обоих
случаях — намеренно: на экране входа в сервис психологической помощи разные ответы
были бы способом узнать, зарегистрирован ли человек.

## Шаг 5. Чего не делать

1. Не удалять и не переупорядочивать существующие провайдеры.
2. Не менять `AUTH_SECRET`.
3. Не ставить `allowDangerousEmailAccountLinking` никому, кроме нашего issuer.
4. Не переносить `User.id` и не делать `UPDATE` по идентификаторам.
5. Не включать единый вход единственным способом, пока не пройдут две недели наблюдения.

## Шаг 6. Ссылка на аккаунт СИМПАС

В продукте человек управляет тем, что относится к продукту. Всё, что относится к его
личности — сведения о себе, способы входа, устройства, согласия и рассылки, — живёт в
кабинете на нашем домене. Ссылка на него нужна там, где человек её ищет: в настройках
профиля.

```
https://auth.cmpas.ru/account?return_to=practice
```

`return_to` — **код продукта**, не адрес: свободная форма не принимается (У-3, открытый
редирект). Допустимые значения: `practice`, `zapiski`, `moments`, `steps`.

Зачем он нужен: по нему кабинет показывает человеку обратную дорогу — «← Вернуться в
ПРАКТИКУ» в шапке каждого экрана. Без параметра кабинет считает, что человек пришёл сам
(набрал адрес руками), и обратной дороги в продукт не предлагает — придумывать её было бы
неправдой о его пути.

Адресуются и разделы напрямую, чтобы не заставлять искать:

| Куда | Адрес |
|---|---|
| Обзор | `/account?return_to=practice` |
| Личные данные | `/account/personal?return_to=practice` |
| Безопасность: способы входа, устройства | `/account/security?return_to=practice` |
| Устройства и сеансы | `/account/devices?return_to=practice` |
| Письма и уведомления | `/account/communications?return_to=practice` |
| Согласия и документы | `/account/privacy?return_to=practice` |

Вход в кабинет отдельный от входа в продукт не нужен: если сессия СИМПАС жива, человек
попадает туда без единого экрана.
